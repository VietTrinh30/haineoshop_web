3 Approaches to Product-Scoped Variants

Click to select the approach you prefer — my recommendation is Approach A

A

Scope Existing Plugin Collections by Product RECOMMENDED

Keep plugin infrastructure, add product ownership

Data Model Changes
// variantTypes collection — add product field
variantTypes {
label: "Loại"
name: "loai"
+ product: → products // NEW! scopes to product
options: → join variantOptions
}

// variantOptions — no change needed
// (already scoped via variantType)

// variants — no change needed
// (already has product field)
✅ Pros
  • Minimal changes to plugin structure
  • All existing relationships preserved
  • Cart/Order variant references still work
  • Plugin's variant hooks (validation, beforeChange) still work
  • Easy to filter: where: { product: { equals: productId } }
⚠️ Cons
  • Need custom admin component for inline editing
  • Variant types/options still separate DB documents
  • Need cleanup hooks on product delete
How auto-generation works:
Product beforeChange hook → when variantTypes/options change → CRUD variant types & options docs → compute cartesian product → create/delete variant docs
B

Inline Types/Options in Product, Keep Variants Collection

Embed type/option definitions inside product, only variants stay separate

Data Model Changes
// Product — inline arrays
product {
+ variantTypeDefs: array [
{ label, name,
options: array [
{ label, value }
] }
]
}

// variants — change options field
variant {
product: → products
options: → variantOptions
+ options: json [{typeId, optionId}]
}

✗ DELETE variantTypes collection
✗ DELETE variantOptions collection
✅ Pros
  • Cleanest per-product data model
  • No orphan records possible
  • All type/option data lives on product
⚠️ Cons
  • Breaks plugin's VariantOptionsSelector component
  • Cart/Order references to variant options break
  • Gallery variantOption relationship breaks
  • Need to rewrite variant option matching logic everywhere
  • High migration risk — many frontend components affected
C

Fully Inline Everything (Types + Options + Variants)

Everything embedded inside the Product document

Data Model Changes
// Everything inside Product
product {
+ variantTypeDefs: array [...]
+ variantRows: array [
{ options: json,
price, inventory, sku }
]
}

✗ DELETE variantTypes collection
✗ DELETE variantOptions collection
✗ DELETE variants collection
✅ Pros
  • Simplest data model — single document
  • No orphan records
  • Atomic saves
⚠️ Cons
  • Breaks cart & order item references entirely
  • Can't query individual variants (inventory, reporting)
  • Product documents become very large
  • Plugin's payment validation completely breaks
  • Highest risk — most code rewrite required
