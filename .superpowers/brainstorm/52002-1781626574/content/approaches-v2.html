Updated Analysis: Simple Types/Options

Since variant types & options only need id + label, the picture changes

💡 Key Insight
Payload's array fields auto-generate a unique id (string) per row. Since you only need id + label for types/options, inline arrays are a perfect fit — no need for separate collections with timestamps, soft delete, ordering, etc.
A

Keep Plugin Collections (scope by product)

Same as before — add product field to variantTypes

What you get per variant type:
id: number ← auto
label: string ✓ need
name: string ✓ need
updatedAt: string ← unnecessary
createdAt: string ← unnecessary
deletedAt: string ← unnecessary
_order: string ← unnecessary
⚠️ Separate DB documents for data that's just id + label feels like overkill
Downsides with simple data
  • 3 separate collections for very simple data
  • Need orphan cleanup hooks
  • Each type/option = separate DB document + separate API call
  • More moving parts for something that's just id + label
  • Still need custom admin component anyway
B

Inline Types/Options + Keep Variants Collection NOW RECOMMENDED

Types & options as product arrays, variants stay separate for cart/order

Product Document
product {
title, price, gallery, ...
enableVariants: checkbox
variantTypeDefs: array [
id: string (auto)
label: "loại"
options: array [
id: string (auto)
label: "DAY - Có màu"
]
]
}
Gallery (updated)
gallery: array [
image: → media
variantOptionId: text
// stores inline array item id
]
Variants (kept, modified)
variant {
product: → products
options: json [{typeId, optionId}]
price, inventory, sku
}
✅ Pros
  • Natural fit — id+label is exactly what arrays give you
  • No orphan records — types/options deleted with product
  • Single document save for types/options
  • Variants still separate (queryable for inventory/cart/order)
  • Cart/Order → variant relationships preserved
  • Simpler admin UI — standard Payload array fields
  • Fewer API calls — no CRUD for type/option documents
⚠️ Changes needed
  • Gallery: variantOption relationship → text field
  • Variant: options relationship → json/array field
  • VariantSelector component: read from product inline data
  • Plugin's VariantOptionsSelector: replaced by custom component
  • Override variant's validateOptions hook
📊 Impact Summary
  • Cart items → variant → still works (variant has id)
  • Order items → variant → still works
  • Gallery → option → minor change (relationship → text)
  • Frontend VariantSelector → reads from product
  • Delete variantTypes, variantOptions collections → clean up
Auto-generation flow:
Product afterChange hook → read inline variantTypeDefs → compute cartesian product of all options → diff against existing variants → create missing / delete removed variant docs
